## D-001 引擎版本与渲染器（已采纳，T001）

- 固定 **Godot 4.7.2.stable**（开发机已安装的版本）。规范只写了 “4.x”，不固定会导致 `.tscn` 格式和 `.uid` 文件来回漂移。
- 渲染器用 `gl_compatibility`：纯 2D 不需要 Forward+，而 Compatibility 在老旧 PC 和集显上覆盖面最广。
- 显示：基准视口 1920×1080，`canvas_items` + `expand` 拉伸，开发窗口默认 1280×720，像素图形使用 nearest 过滤并开启 2D 像素吸附。
- 替代方案：Forward+（2D 用不上它的优势）；`viewport` 拉伸模式（像素更锐利，但 UI 文字在 720p 下会更糊）。

## D-002 测试框架（已采纳，T001）

- 自写零依赖执行器 `tests/run_tests.gd`（SceneTree 脚本）+ 断言基类 `tests/framework/test_case.gd`。自动发现 `tests/test_*.gd` 中的 `test_*` 方法；有失败、脚本无法编译或测试数为 0 时，退出码为 1。
- 测试脚本按**路径** `extends` 基类，不依赖 `class_name`，这样在 `.godot` 缓存缺失时也能报出清晰的错误。
- `tools/check.sh`：import → 测试 → 主场景无头启动 30 帧；日志中出现 `ERROR` / `SCRIPT ERROR` 即判失败。这样“无新增报错”这条验收可以由机器判定。
- 替代方案：GUT（MIT 许可证，功能更全）。没选它是因为多一个需要锁定版本的插件，而核心规则测试用不到它的高级功能。以后需要 mock 或参数化测试时可以再评估。

## D-003 中文字体（已采纳，T001；T019/T020 复核）

- Godot 默认字体没有 CJK 字形。主题字体用 `SystemFont` 回退链：Noto Sans CJK SC → Source Han Sans SC → Microsoft YaHei → PingFang SC → WenQuanYi Micro Hei。
- 风险：在没装中文字体的 Linux 上会显示方块。**发布前（T020）需打包 OFL 授权的 CJK 字体子集**（如 Noto Sans SC 子集），并附上许可证文件。

## D-004 规范评审发现的问题与默认处理

以下问题不阻塞 T001–T004，处理方式按规范 §0 “选择默认值并记录”给出。**2026-11-21 产品负责人已全部批准**；标为“提议”的条目在对应任务中落地。

### D-004a 权威写入口的时序矛盾（已采纳，2026-11-21 获批，作为 T004b 实施）

- 问题：§2.1 和 §12.2 要求 `CommandProcessor.apply()` 是唯一的权威写入口，但对应的 T021/T022 排在 T001–T020 之后。如果 T007（经济）、T010（工资）、T011（房租）、T014（关系）先直接写状态，T021 就会变成横跨所有系统的重构，违反“不要一次性重构全部模块”。
- 默认处理：在 **T004 之后、T007 之前**插入 **T004b**：最小 `WorldState`（纯数据，可序列化）+ `CommandProcessor`（validate → apply → emit，失败不留部分状态）+ `DomainEvent`（带 `event_id`、`game_minute`、`actor_id`、`cause_id`、`payload`）+ 命令幂等 ID。T021/T022 则改为“加固与补全”（revision 冲突检测、有界日志、重放测试）。
- 这样做不违反“T003 不预先实现 T010”：T004b 只提供骨架，不包含任何业务命令。

### D-004b `EconomyService` 与 `CommandProcessor` 的关系（已批准，T007 落地）

- 问题：§3.6 写的是“所有金钱变更必须经过 `EconomyService.try_debit()/credit()`”，§2.1 又规定 `CommandProcessor` 是唯一写入口。两者谁在上层没有说明。
- 默认处理：领域服务（Economy/Work/Housing/…）是**命令处理器在事务内调用的规则模块**，负责校验和计算，状态写入在事务提交时统一落地。UI、剧情和 NPC 只能提交命令，不持有服务的写引用。

### D-004c 旧版事件效果与“剧情不得直接改值”冲突（提议，T015）

- 问题：§4.3 的事件白名单包含 `credit_money`、`debit_money`、`change_relationship` 这类直接改值的效果；而 §14.2 和 §12.2 禁止剧情直接加钱、改关系。
- 默认处理：事件效果在解释时**翻译为系统命令**（`actor_id = "system:event/<event_id>"`），经 `CommandProcessor` 执行。一个事件的全部效果作为一个事务执行：任意一条失败（例如 `debit_money` 余额不足）就整体回滚，并记录稳定的错误码。

### D-004d 七日经济缺乏压力，且关键速率未给出（提议，T008/T018）

- 问题 1：按 §3.4 的数值，初始 ¥1,500、房租 ¥600/7 天、每天约两份简餐 ¥36，**完全不工作也能在第 7 天交上房租**（1500 − 600 − 252 ≈ ¥648 余额）。这样“打工”缺少动机，T018 要求的“过度消费路线会触发经济压力”也很难成立。
- 问题 2：规范没有给出饥饿、精力、压力随时间变化的速率，也没有给出各岗位班次的精力和压力消耗，以及押金规则。
- 默认处理（均为游戏化参数，T018 再调）：
  - 签约时收押金 ¥600（可退，计入流水）；第 7 天交首期房租 ¥600。结合下面的饥饿速率（约 80 点/天，约等于每天 ¥40 的简餐），不工作时 7 天后余额约为 ¥0–50，处于“勉强”状态：轻度过度消费就会欠租，只要上 2 个班就能明显宽裕。
  - 清醒时每小时：饥饿 +4、精力 −3、压力 +0（饥饿 ≥ 70 时压力每小时 +2）。睡眠期间每小时：饥饿 +2，精力恢复到最多 90（按 §3.4）。
  - 班次每小时：便利店精力 −5 / 压力 +2，餐饮精力 −6 / 压力 +3，仓储精力 −9 / 压力 +3。
  - 以上数值写入 `content/regions/cn/policy_config.json` 与 `content/common/needs.json`，不进代码。

### D-004e 工资取整（提议，T010）

- 工资按 `hourly_minor * minutes / 60` 计算，结果**向下取整到分**，按实际完成的班次分钟数结算。整个计算全程使用整数，在 RegionPolicy 计算税后之前完成。

### D-004f Day 3 “同事邀请吃饭”的前提可能不成立（提议，T015）

- 问题：如果玩家 Day 2 没有上班，Day 3 就不存在“同事”。
- 默认处理：条件化。若已完成过任意班次，由该岗位的同事 NPC 发出邀请；否则由便利店 NPC（Day 2 认识的人）以“邻居 / 熟人”身份发出邀请。如果两者都不满足，则不触发（符合 §14.1 “可以不发生故事”）。

### D-004g 本地化文件格式（已被 D-013 取代）

- 默认处理：采用 Godot 原生格式，每个内容包一个 CSV（如 `content/common/localization/strings.csv`、`content/regions/cn/cities/linchuan/strings.csv`），列为 `keys,zh_CN,en`，英文列可以暂时为空作为占位。

## D-007 时间推进与信号（已采纳，T003/T004b）

- `GameClock` 只负责状态和计算，**不发信号**。`advance_minutes(n)` 在每个午夜处切分，返回有序的事件草稿：`time_advanced(old, new)`，跨日时再加 `day_changed(day)`。
- 草稿由 `CommandProcessor` 转成 `DomainEvent`，命令提交后再由 `GameEventBus` 转发为信号。这样回滚的命令不会“泄漏”任何通知。这一点对应规范 §4.2 “Signals 是通知通道，不是事实来源”。
- 探索时的时间流逝：`accumulate_real_time(delta)` 只计算到期的整数分钟数，由会话层提交 `advance_time` 命令（T005/T006 接入）。时钟本身不会绕过命令处理器自行前进。
- 暂停原因是一个集合（dialogue/menu/save…），全部移除后才恢复。暂停状态、倍率和余数属于会话状态，不存档。
- 单次推进上限为 30 天（`MAX_ADVANCE_MINUTES`），防止事件风暴（§13.4）。
- `advance_time` 只允许 `player` 和 `system[:…]` 发起，**NPC 不能推进世界时间**。
- 第 1 天 00:00 对应第 0 分钟；城市开局时间为 `minute_from_day_time(starting_day, starting_hour)`。日期键暂用 `day_N`，以后接入真实日历时只需替换 `date_key_of`。

## D-008 内容包格式（已采纳，T002）

- 每个包目录有一个 `pack.json`，包含 `pack_id`、`pack_version`（semver）、`scope`（`region_id`/`country_id`/`city_id`）、`dependencies`、`files`（路径 → 表名）、`story_providers`（`provider_id`/`schema_version`/`provider_version`）。注册器会额外计算 `content_hash`（manifest 加全部数据文件的 SHA-256），供 §16.3 存档记录使用。
- 数据文件必须带 `schema_version`。数据可以写成单个对象（如 `city.json`，与规范 §2.5 一致），也可以写成 `{"schema_version", "records": [...]}`。
- 各表的模式集中写在 `ContentSchemas`，字段多出、缺少或类型不对都会报错，防止拼写错误被静默忽略。**新增城市或地区不需要改代码**，只有新增“数据种类”时才需要。
- ID 规则：地理实体（地区 `CN`、城市 `CN_LINCHUAN`、片区 `OLD_TOWN`）沿用规范示例中的大写格式；其余实体一律用 `snake_case`。
- 新增 `districts.json` 和 `locations.json` 两张表。规范 §2.4 没有列出它们，但 `city.default_spawn`、NPC 的 `location_id`/`home_location_id` 都需要被引用的目标。
- 引用可见性：一个包只能引用自身或（传递）依赖包里的记录（`E_REF_NOT_VISIBLE`）。
- 跨记录一致性用模式里的 `match` 声明，而不是写专门的代码。例如：城市与地区的货币必须一致；片区和出生点必须属于同一城市；地区的规则配置必须指回该地区。
- 加载是全有或全无的：一次报告全部错误（文件 + JSON 指针 + 稳定错误码），失败后注册器为空。
- 库代码从不打印；入口场景负责把错误 `push_error` 出来。
- 暂未实现：`text_key` 是否在本地化表中存在的检查。本地化表在 T014/T019 建立后再加。

## D-009 命令内核事务模型（已采纳，T004b）

- `WorldState` = 修订号 + `CommandJournal` + 若干命名组件。组件需实现 `to_dict()` / `from_dict() -> 错误码`，现在只有 clock，之后会加入 wallet、needs 等。
- 事务方式是“先捕获、失败回滚”。MVP 的世界很小，整体捕获的成本可以接受；状态变大后（T021）再考虑写时复制或差量记录。
- 命令流水线：结构校验 → 查找处理器 → 幂等检查 → 修订号检查 → `authorize` → `validate` → `apply` → 提交。
  - `authorize`/`validate` 必须只读：处理器会对比前后快照，有改动即判为 `E_HANDLER_CONTRACT`。
  - 事件只能在 `apply` 阶段发出；`apply` 返回任何错误都会整体回滚，事件编号也会回退。
- 幂等规则：
  - 只记住**成功**的 `proposal_id`。失败的命令没有改变任何状态，用同一个 ID 重试是安全的。
  - 同一个 ID 搭配不同请求内容，会返回 `E_PROPOSAL_ID_REUSED`。
  - 记忆窗口为 4096 条，先进先出，随存档保存。业务层仍要自己防重（例如按 `shift_id` 只付一次工资），不能只依赖这个窗口。
- 事件编号 `evt_%08d` 来自存档内的序号，读档后会接着往下编。事件日志最多保留 2048 条，不进存档（§13.1：快照为主）。
- `expected_world_revision = -1` 表示不检查修订号（玩家 UI 默认如此）；不为 -1 时，若修订号不一致返回 `E_REVISION_CONFLICT`。
- 处理器内部不能嵌套提交命令（`E_REENTRANT_COMMAND`）。`committed` 信号的订阅者可以提交后续命令，它们会在当前命令结束后执行。
- T021/T022 剩余工作：按快照+命令日志做重放测试、组件变多后的性能、`ObservationService`。

## D-010 地区规则的选择与中国参数（已采纳，T004）

- 地区规则配置里的 `implementation` 字段指定实现 id（如 `china`），由 `RegionPolicyRegistry` 映射到脚本。选择路径完全由数据决定：城市 → 地区 → 规则配置 → 实现。新增国家只需要新增一个实现和一份配置。
- `settings` 对内容注册器是透明的，由具体实现自行按模式校验，错误信息带上 `/settings/...` 路径。
- 中国参数（游戏化）：工资扣减 5%，扣减额向下取整到分，对玩家有利；每日工作上限 720 分钟；周期成本倍率和日历修正暂时为空。
- 地区的 `currency_code` 和 `country_id` 设为可选，以便将来把 EU 作为地区组，再按国家分别建包（§2.2）。

## D-011 JSON 数值规范化（已采纳）

- Godot 的 JSON 解析器把所有数字解析为浮点。`SchemaValidator` 会把在安全整数范围内的整值浮点转换成 `int`，`any` 类型同样处理；带小数的值在 `int` 字段上报错。
- 因此金额从文件一进入系统就是整数。来自 JSON 的命令和代码构造的命令，指纹也保持一致。
- `any` 接受 JSON `null`（已保存的 `CommandResult.error_code` 就是 null）。

## D-012 测试卫生（已采纳）

- `tools/check.sh` 遇到 `ObjectDB instances were leaked` / `resources still in use` 也判为失败：这类日志几乎都意味着 RefCounted 循环引用（例如捕获了 owner 的 lambda 连接到 owner 持有的对象）。测试需要在 `after_each` 中断开这类连接。

## D-013 本地化改为内容包内的 `text` 表（已采纳，M1；取代 D-004g）

- 每个内容包新增 `text.json`，格式为 `{"id": "<text_key>", "zh_CN": "...", "en": "..."}`。`zh_CN` 必填，`en` 可留空，留空时回退到中文。
- 所有 `*_key` 字段都按引用校验：key 不存在或不可见都会报错，补上了 D-008 遗留的“text_key 存在性校验”。
- 运行时由 `Localizer` 生成 Godot `Translation` 并注册，界面直接用 `tr(key)`。
- 不采用 Godot 原生 CSV 导入，原因是：CSV 会被编辑器自动导入成 `.translation` 文件并要求写进项目设置，内容包就无法自成一体；导出时还会和 JSON 一样遇到额外的打包问题（D-004h）。
- 新增语言（如 `de`）需要在 `ContentSchemas` 的 `text` 表加一列，属于模式变更。

## D-014 地图与玩家（已采纳，T005）

- 一张连续的老城街区地图，40×20 格，每格 32px。地图用 ASCII 行加图例写在 `maps/old_town.json`，由内容校验检查形状、图例、越界、出生点可走、交互点必填字段。
- **首版没有室内场景**：出租屋、便利店、快餐店都通过门口的交互点使用。规范 §4 列出的 `interiors/*.tscn` 暂不制作，需要时再加。
- 占位图块在运行时生成纯色贴图，不引入任何美术素材（§6）。不可通行的图块（墙、建筑、树、水）带整格碰撞。
- 碰撞层：1 = 世界，2 = 玩家，3 = 交互物。
- 4 向移动：最后按下的方向键生效，不走斜线；松开后回落到仍按着的键。
- 交互：玩家身上的感应区选最近的交互物，按 E 交互。交互物分三类：`sign`（显示文本）、`shop`（打开商店）、`activity`（确认后执行，例如睡觉、长椅休息）。
- 城市地图可以直接运行（编辑器 F6，或 `godot res://scenes/world/city_world.tscn`），会通过 `GameSession` 自动开新游戏。`check.sh` 也用这种方式无界面启动 60 帧。

## D-015 时间流、需求与活动（已采纳，T006/T008；落地 D-004d）

- `TimeFlow.advance(ctx, 分钟, 模式)` 是命令内推进时间的唯一入口：探索、吃东西、睡觉、休息都走这里，以后的打工和通勤也会走这里。它在每个午夜切段，逐段调用组件的 `on_time_passed`，跨日时调用 `on_day_started`（T011 房租会挂在这里）。事件按所在时间段打时间戳。
- 探索时间：真实 1 秒 = 游戏 1 分钟，每满 5 游戏分钟提交一次 `advance_time`（`game_rules.json`）。打开任何面板时，场景树和时钟都暂停。
- 需求速率（每小时，可在 `needs.json` 调整）：

  | 需求 | 清醒 | 休息 | 睡眠 | 其他 |
  |---|---|---|---|---|
  | 饥饿 | +4 | +3 | +2 | — |
  | 精力 | -3 | +2 | +10 | 睡眠恢复上限 90 |
  | 压力 | 0 | -4 | -2 | 饥饿 ≥70 或精力 ≤20 时每条 +2 |

  余数以整数累积，所以 60 次 1 分钟推进与 1 次 60 分钟推进的结果完全相同。压力规则在每小时开始时判定。
- 活动写在 `activities.json`：睡觉 480 分钟（睡眠模式），长椅休息 60 分钟（休息模式）。**目前不检查是否租房或是否在场**：租约检查在 T011 加入，玩家位置在 T012 加入。

## D-016 经济、物品与商店（已采纳，T007）

- `EconomyService` 是世界组件，管理钱包和流水。只有在命令的 apply 阶段才能写入，UI 和剧情直接调用会得到 `E_NOT_IN_COMMAND`。余额不能为负；每笔流水带 `transaction_id`、游戏分钟时间戳、原因、带符号金额、币种、余额和事件 ID。流水在存档中保留最近 200 条。
- 物品的**效果**放在 common 包（`items.json`，不分地区），**价格**放在城市包（`shops.json`，按地区币种）。使用物品要花时间：简餐 20 分钟、速食 10 分钟、饮料 0 分钟。
- 背包每种物品最多 99 个（`game_rules.json`）。
- 商店界面列出每件商品的名称、效果、价格、“买后剩多少”。买不起的商品显示“钱不够”并禁用按钮，不只靠颜色提示（§6）。

## D-017 Autoload 与事件信号（已采纳，M1）

- Autoload 只有两个：`EventBus`（`GameEventBus`）和 `GameSession`（保存内容和当前 `SimulationSession`），符合 §0 对单例的限制。世界状态本身不放进单例。
- `GameEventBus` 的信号比规范 §4.2 的建议多带一个 `owner_id`：`wallet_changed(owner_id, balance)`、`need_changed(owner_id, need_id, value)`、`inventory_changed(...)`。以后 NPC 也会有钱包和需求，没有 owner 就分不清是谁的变化。
- HUD 在每个已提交的事件后，从 `SimulationSession.view_player()` 整体刷新一次，不在界面里自己累加数值。

## D-019 3/4 斜俯视表现层（已采纳，T005b，2026-11-21 由产品负责人选定方案 A）

- 采用星露谷式 3/4 斜俯视 2D 像素画法。HD-2D 等到 7 日流程可玩、正式美术立项时再评估（规范 §19）。

## D-020 位置以地图为粒度（已采纳，T012）

- 权威位置 = 所在地图 + 最后到达的地点（`LocationSystem`）。地图内的走动只属于画面表现，不提交命令。
- 每个地点在 `locations.json` 中声明所属 `map_id`。买东西、上班、签约、睡觉、乘车、长椅休息都要求人在对应地点的地图上，否则返回 `E_NOT_HERE`。
- 不要求精确站位，避免每走一步都提交命令；以后如需更细的粒度（如必须站在柜台前），再加“到达地点”命令。

## D-021 打工、房租、通勤的规则细节（已采纳，T009–T012；落地 D-004d/e）

- 班次 ID 为 `<job>.d<day>.<template>`，只能预约今天还没开始的班次和明天的班次。状态流转：booked → in_progress → completed；没去上的班次在结束时间过后标为 missed。
- 预约时检查：岗位从第几天开始招人、时间是否与已有班次重叠、地区规则的每日工时上限（中国游戏化参数为 720 分钟）。
- 上班：最多提前 120 分钟到，早到就等到开班；最晚在下班前 30 分钟开始，迟到按实际工作分钟计薪。工资 = 时薪 × 分钟数 / 60，向下取整到分，再由地区规则算出到手金额。
- 工资只在 in_progress → completed 时入账一次，同一班次不可能重复付薪。命令 ID 重放也不会重复执行（测试覆盖）。
- 工作期间的需求变化使用岗位自己的每小时速率（时间模式为 `working`）。
- 房租：签约时付押金，首期房租在签约日 + 6 天（即第 7 天）开始时自动扣，之后每 7 天一期。扣不到时记为欠租，余额不会为负；此后每天开始时重试，也可以手动补交。跨多天快进时逐日结算，`next_due_day` 只在付款成功后前进，所以不会重复扣款，也不会漏扣。
- 没有租约不能在出租屋睡觉（`E_NO_HOME`）。存在押金后，不打工时 7 天后余额约 ¥0–50，详细调参见 T018。
- 公交：12 路往返老城和工业区，票价 ¥3，车程 30 分钟，06:00–22:00 发车。钱不够或不在运营时间都不能乘车，状态不变。

## D-022 剧情 DSL、事件与 StoryValidator（已采纳，T015）

- 条件类型在规范 §4.3 的白名单基础上扩展了：时间段、钱包、需求上下限、任意关系、租约和欠租状态、班次数、统计计数、所在地图、NPC 是否在场、事件是否已触发。效果类型仍是规范白名单里的 5 种，外加只允许在事件中使用的 `show_summary`。
- 未知类型、缺少或多余字段、错误的值类型、引用不存在的人物或物品，加载时都会失败。
- `StoryValidator` 的权限限制：
  - 剧情 flag 必须放在 `story.` 命名空间下；
  - 单次金钱变化不超过 ¥200；
  - 关系变化不超过 ±20，需求变化不超过 ±50；
  - 对话里的效果只能放在终止选项上，这样重新开始对话也无法重复领取效果；
  - 事件暂时只允许一次性（`once`），可重复事件等 T028 做冷却规则时再支持。
  它在每次加载内容时运行，也可用于外来的故事数据（目前是测试样例，将来是模型输出）。
- 每次命令成功后，会话执行一轮剧情检查：按优先级（相同优先级按 ID）触发可触发的事件，然后推进条件已满足的任务步骤。每个动作都是一个独立的系统命令，例如 `system:event/<id>`、`system:quests`，并在命令里重新检查条件。一轮最多 8 步，防止事件风暴；失败的事件保持未触发状态，之后还会再试。
- 事件的全部效果在一个命令里执行，任一失败就整体回滚（D-004c）。已触发的记录保存在存档中，读档后不会重复触发（§8.1 EventOnce）。
- 第 7 天的阶段总结按钱、工作、人际、身体四组，每组取第一条条件成立的文案。触发时就把选中的文案 key 固定进队列，所以读档后看到的总结不变。触发时间为第 7 天 20:00；如果玩家睡过了，就在第 8 天补上。
- 剧情面板（排队中的对话和总结）必须作答，所以在剧情面板上按 Esc 会打开暂停菜单而不是关闭面板。主动发起的 NPC 对话按 Esc 可直接离开。

## D-026 存档格式与安全写入（已采纳，T017）

- 一个存档是一个 JSON 文件 `user://saves/slot_0N.json`，共 3 个位置。文件外层是信封，包括：
  - `save_schema_version`、`game_version`、保存时间（真实时间，仅作显示）；
  - `region_id`、`city_id`、`currency_code`，以及每个内容包的版本与哈希；
  - `player`：`scene_id`（地图）、`spawn_id`（最后到达的地点）、`tile`（站立格子，仅用于表现）；
  - `clock_minute`、列表摘要、`rng`（目前没有随机规则，先占位）、`proposal_seq`。
- 信封里包着 `WorldState.to_dict()`。规范 §4.4 要求保存的钱包、流水、需求、背包、工作、住房、关系、旗标都是其中的组件，事件、剧情队列、任务也在里面。
- 写入流程：写 `.tmp` → 从磁盘读回，按正式读档的流程完整还原一遍 → 把旧档改名为 `.bak` → 把新档改名为正式文件。任何一步失败都会删除临时文件，旧档不受影响。如果主文件缺失（例如两次改名之间断电），读档时会自动使用 `.bak`。
- 读档流程依次是：大小限制 → JSON 解析 → `SaveMigrations` 显式迁移 → 信封校验。之后检查：
  - 内容包必须仍然存在，缺失就报错，不会静默替换；版本不同时只给警告；
  - 城市、地区、货币必须一致；
  - 每个组件自己校验范围和 ID；
  - `SaveManager.check_references` 再查组件自己查不到的 ID，例如物品、事件、对话节点、总结文案。
- 任何失败都不会改动正在进行的游戏。整个过程不反序列化对象，也不执行存档里的任何内容。
- `proposal_seq` 一并保存，所以读档后继续执行同样的命令，得到的世界和日志与没读档时完全一致（有测试）。
- 存档入口：暂停菜单的“保存 / 读取”、出租屋门口的“存档”、标题画面的“读取存档”。覆盖已有存档前会确认，读档前提醒未保存进度会丢失。

## D-028 设置、音效与英文占位（已采纳，T019）

- 设置保存在 `user://settings.cfg`，与存档分开，因为设置属于这台机器，不属于某一局游戏。内容有：主音量、音效音量、窗口（1280×720 / 1600×900 / 1920×1080 / 全屏）、界面语言。改动立即生效并保存；非法值回退为默认值。窗口不会开得比屏幕大。

- 音效全部在运行时合成（点击、收入、新的一天），项目里没有任何音频文件，所以不涉及授权问题。音效走 `SFX` 总线，受音量设置控制。暂时没有背景音乐。
- 标题画面只在自检失败时显示自检信息；正常时把信息并到版本号那一行，方便反馈问题时附上。

## D-029 发布构建与冒烟测试（已采纳，T020）

- `export_presets.cfg` 定义 Linux（x86_64）和 Windows（x86_64）两个预设：单文件，资源包嵌入可执行文件；显式包含 `content/*.json`；排除 tests、tools、docs。Windows 预设不修改 exe 资源，因此不需要 rcedit。

  2. 跑 `check.sh`；
  3. 导出两个平台；
  4. 在一个空目录里运行 Linux 可执行文件的冒烟测试；

- 城市专属的活动放在临川城市包自己的 `activities.json`；common 包只保留通用活动（睡觉、在家休息、长椅）。
- 地图新增两项，都只用于表现，不进入世界状态、不进存档：
  - `decor`：可穿行的景物，包括凉亭、路灯、花坛；
  - `ambient`：公园里的人，包括下棋、围观、唱歌、拉二胡、广场舞、太极、钓鱼、路人。他们按所属活动的时段出现，或按自己的时段出现，所以从人群就能看出“现在有什么”。
  
  这些人只有简单的动作动画，不能交互，也不挡路，和命名 NPC 一样。
- 修复：带自动换行描述的菜单（在家休息、游戏厅）第一次测量高度时，文字按一行计算，导致底部按钮被裁掉。现在会在排版完成后的下一帧重新测量，并有回归测试。

## D-032 像素画风：人物与场景（已采纳，产品负责人反馈）

- 反馈：人物要更接近掌机 RPG 和农场模拟游戏的样子，现在看不出男女；场景也要更好看。
- 只借鉴这类游戏的通用画法，不复刻任何具体游戏的角色、素材或画面：
  - Q 版大头身，头约占身高 40%；
  - 1 像素描边，颜色取所描形状的深色；
  - 光从左上来，两三档明暗；
  - 低分辨率绘制后放大 2 倍，用最近邻过滤。
  
  所有图像仍由代码在运行时绘制，项目里没有图片文件（D-003）。
- `PixelArt`：小画布，提供自动明暗、自动描边、放大绘制和纹理缓存。可以在无界面模式下生成，所以 `tools/sprite_sheet.gd` 能不开窗口地导出人物总览图，用于审阅。
- `PixelPerson`：20×28 的人物，4 个朝向、4 帧走路，另有坐、举手、平举、前伸、张嘴唱歌、眨眼等姿势。外观数据（NPC 的 `appearance` 和地图的 `ambient`）新增以下可选字段：
  - `hair_style`：短发、刺猬头、平头、谢顶、长发、波波头、马尾、盘发、烫卷发；
  - `outfit`：裤装、裙装、连衣裙；
  - `figure`：`f` 表示窄肩，并有睫毛和腮红；
  - `skin`、`bottom`、`shoes`，以及工作马甲 `vest`。
  
  性别主要靠发型和服装区分，其次靠脸部细节。
  
  | 角色 | 外观 |
  |---|---|
  | 陈雨 | 年轻女店员，马尾，绿色店员马甲 |
  | 王阿姨 | 烫卷发，穿裙子 |
  | 老周 | 谢顶的大叔 |
  | 玩家 | 刺猬头、蓝外套的年轻人 |
  
  公园里的人各自配了外观：下棋的是谢顶大爷，唱歌和跳舞的多是盘发或卷发的阿姨。
- 场景：
  - 地面：每格 16×16 像素，每种地面 4 个变体，按格子坐标的哈希挑选，避免重复感。地砖有缝和倒角，草地有草叶和小花，柏油路有颗粒，水面有波纹。
  - 衔接：草地边缘是参差的草沿，河岸有石沿和浪花，路沿更立体；行道树放在铺装树池里。
  - 道具：树（3 种，其中一种开花）、花坛、路灯、长椅、公告栏、公交站牌、象棋石桌、音箱、凉亭，全部是描边像素画。
  - 建筑：整栋按每格 16 像素绘制，包括瓦片屋顶、屋脊翘角、檐口，不同风格的墙面（砖墙、瓷砖、铁皮、灰泥），带窗框窗台的窗户（部分有窗帘、绿植或空调外机）、店面橱窗、条纹雨棚和门。
  - 文字：店招和 NPC 名字由 `WorldText` 以平滑字体绘制，像素画保持锐利、文字保持清晰。不使用界面控件 Label，因为它会套用主题的边距和字号，在世界坐标里算出的尺寸不对。
- 同时修复：切换界面语言后，HUD 的需求数值在下一次游戏事件之前一直是空的（D-028 引入），现在重建时立即刷新，并有回归测试。

## D-033 捏人（已采纳，产品负责人反馈）

- 新游戏流程改为：标题 → 创建角色 → 进城。在出租屋照镜子可以随时改造型。
- 可调项：
  - 名字（可留空，最多 12 字）、性别；
  - 发型：9 种，任何性别都能选；
  - 发色 8 种、肤色 5 种、上衣颜色 10 种；
  - 下装：裤子、短裙、连衣裙，另有 7 种颜色；
  - 鞋子颜色 5 种。
  
  左边是会走动、可转身的大预览，另有“随机”按钮。切换性别时会顺带推荐对应的发型和下装，推荐后仍可任意修改。
- 名字和外观存在新的世界组件 `profile` 里（`ProfileSystem`）：
  - 只用于表现，不影响任何规则；
  - 新游戏时随世界一起初始化；
  - 之后只能通过 `set_profile` 命令修改，要求已租房并在家，与“照镜子”对应；
  - 读档时按白名单严格校验：发型和下装只能取预设值，颜色必须是 `#rrggbb`，名字长度有限且不能含控制字符。
- 存档格式升到第 2 版。`SaveMigrations` 第一次真正派上用场：第 1 版存档会自动补上默认外观和空名字，有测试覆盖。
- 名字显示在日志标题和存档列表里。
- “随机”按钮只用于界面，不影响游戏规则的确定性。
- 已有的人物画法（D-032）保持不变：玩家和 NPC 共用 `PixelPerson`。

## D-034 能走进去的店：室内场景（已采纳，产品负责人反馈）

- 反馈：便利店和快餐店要能走进去。将来打工可以做成以店内场景为主的小游戏。
- 室内就是普通地图（`map_convenience_interior`、`map_fast_food_interior`），沿用同一套地图、渲染、存档与在场规则（D-020 按地图判断在场）。
  - 新增地块：`floor_tile`（瓷砖地）、`floor_wood`（木地板）、`wall_in`（3/4 视角下看到的墙面，自动加顶线和踢脚线）、`void`（室外的暗色，最下一行在门口留一个缺口）。
  - 小房间的镜头范围会向四周对称扩展，所以房间居中显示。
- 门：交互点新增 `door` 类型，带 `target_location_id`。命令 `use_door {door_id}` 要求玩家在门所在的地图上，然后把玩家移到目标地点；不花游戏时间，所以平衡数据完全不变（报告逐项一致）。
- 地点调整：
  - `convenience_store`、`fast_food_restaurant` 移到各自的室内地图；
  - 老城新增 `convenience_store_front`、`fast_food_front`（类型 `entrance`），出门后站在这里。
  
  玩家的地点原本只会落在公交站，所以旧存档不受影响。
- 结果：买东西和上班都要进店，在柜台办理。依据同一套在场规则，NPC 也跟着进了店：
  - 陈雨 8:00–16:00 站在收银台后面（地图新增 `anchors`，可以指定站位、坐姿和朝向）；
  - 老周 20:00–21:30 坐在快餐店里吃饭。
  - **剧情变化**：陈雨在第 2 天的自我介绍，以前上午 9 点在街上就会自动触发；现在要等你进店，或傍晚 16:30–19:00 在公园遇到她才会触发。这样更合理，而且新手指引本来就会让你进店买吃的。
- 家具（`furniture`）：y 排序的像素画，阻挡它占的格子；椅子和门垫可以穿过。种类有冷柜、货架、收银台、零食架、点餐台、后厨、桌椅、绿植、饮料机、垃圾桶、门垫。墙面装饰（`wall_decor`）有菜单牌、海报、钟、窗、烟酒货架、价签横幅。
- 背景人物新增两种姿势：`eat`（坐着吃饭）、`browse`（站着挑货或忙活）。快餐店有厨师和饭点的食客，便利店有不同时段的顾客。
- **打工小游戏的规划（尚未实现）**：
  - 收银台（`counter_convenience`）和点餐台（`counter_fast_food`）就是工位，现在在这里点“上班”。
  - 以后点“上班”时，可以在当前室内场景里打开小游戏：便利店扫码收银、找零，快餐店按单出餐。
  - 小游戏只产出一个“表现分”，命令层仍是 `work_shift`：
    - 时长、需求变化、基本工资不变；
    - 表现分换算成小费或奖金，经地区规则（`RegionPolicy`）审核后记账；
    - 分数随命令一起记录，读档和重放结果一致。
  - 始终保留“自动完成”选项，表现按中等计算，所以不想玩小游戏的玩家和脚本玩家不受影响。
- 测试：
  - 新增共用辅助函数 `Sessions.go(s, location)`，会自动进出门；
  - 机制测试和平衡脚本都改为先进店再买、再上班；
  - 新增场景测试：进店、在柜台购物、出门回到店门口；家具挡路；房间居中；陈雨站在柜台后。

## D-035 老街之外：新河里、市中心与昼夜（已采纳，产品负责人反馈）

- 反馈：走出老街应该有别的场景，不能只能坐车去工业区。要有普通人生活和工作的街区，比如工地、理发店；要有公交去市中心的繁华商业街，有奢侈品店和高楼；还要有早上、白天、傍晚、夜里四个时段的变化。
- **步行相连**：门新增 `walk_in` 属性，放在街道尽头的格子上，走上去就会进入相邻街区（仍然通过 `use_door` 命令）。老街东头的马路直通新河里，走回西头就回到老街。
- **新河里**（48×26，地区 `XINHE`），是普通人生活和干活的地方：
  - 阿强理发（带转灯柱）、兰州拉面（门面）、两栋老式住宅楼；
  - 带围挡的工地：在建楼有脚手架和绿色安全网，有塔吊、砖堆、值班室；白天 7:00–18:00 有工人在干活；
  - 老小区：晾衣架，傍晚有聊天的阿姨和玩耍的孩子。
  - 新岗位“工地小工”：¥38/小时，7:00 开工，干 6 小时。每小时精力 -11、饥饿 +7，是最累的活，在招聘公告栏里和其他岗位一起显示。
  - 理发：交互点 `barber` 带价格（¥30）和服务时长（30 分钟）。界面复用捏人面板，但只显示发型和发色两项；确认后执行 `get_haircut` 命令：付钱、过时间，并只改玩家形象里的头发。
- **市中心**（56×28，地区 `DOWNTOWN`），坐 1 路公交去（¥4、35 分钟，06:00–22:30，从老街公交站发车）：
  - 四车道马路配斑马线，地面是抛光石材，有喷泉；
  - 三座玻璃幕墙高楼，楼高最多 14 格；为此 `roof_overhang_rows` 的上限放宽到 10；
  - 商铺：LUMEN 精品（手袋 ¥12,800、丝巾 ¥2,600、香水 ¥980）、时光名表（¥36,000）、云端咖啡（拿铁 ¥38：精力 +6、压力 -5）、糖果屋甜品（小蛋糕 ¥45）；
  - 临川中心商场：“逛商场”10:00–22:00，免费，减压，但会累；
  - 街上有逛街的人、上下班的白领和游客。
  - 奢侈品是新的物品类别 `keepsake`（收藏品）：买了会一直在背包里，不能使用（`E_NOT_USABLE`），背包里显示为收藏品。这些价格是“看得见但够不着”，真买下来，第一周的经济会立刻吃紧。
- **昼夜**（`DayCycle` / `DayNight`），只影响画面：
  - 四个时段：清晨 05:00–09:00、白天 09:00–17:00、傍晚 17:00–19:30、夜里 19:30–05:00。HUD 时间旁边显示当前时段。
  - 户外画面按时间叠加颜色：日出偏暖，白天不变，黄昏金红，入夜蓝紫，深夜暗蓝。
  - 天越暗，路灯下的光晕和楼里亮着的窗户就越亮：大约一半住户窗户亮灯，店面橱窗全亮，高楼和商场窗户成片亮起。老街主街新增 8 盏路灯。
  - 室内地图标记为 `indoor`，有灯照明，不随时间变暗。
- 新增地块：`dirt`（工地土地）、`fence`（围挡）、`plaza`（广场石材）。新增建筑风格：理发店、面馆、咖啡、奢侈品、玻璃塔楼、商场、在建楼。新增景物：塔吊、砖堆、晾衣架、理发店转灯柱、喷泉。新增地面标线：斑马线。新增背景人物姿势 `work`（挥锤或挖土）。
- 测试辅助函数 `Sessions.go` 的“出门”兜底只在室内使用，避免在街上被带着走去别的街区。
- **修正（产品负责人反馈）**：
  - 夜里窗户的光原本是盖在整个世界上面的独立图层，会压在人物身上。现在改为：变暗是给每个世界元素单独染色；窗户光是建筑自己的子节点，随建筑一起参与前后遮挡；路灯光晕在地面层，位于人物下面。
  - 退出时的资源泄漏，来源是一直存在的静态缓存：像素贴图、地块图集、音效、光晕纹理、翻译和正则表达式。现在在 `GameSession._exit_tree` 里统一释放，`UiSound` 退出时停止仍在播放的声音。
  - 检查脚本 `check.sh` 是无界面运行的，不会产生显卡资源，所以没发现这个问题。新增 `tools/leak_probe.gd`：开窗口走一遍“新游戏 → 捏人 → 进城 → 退出”，用于人工复查泄漏。
